# 01. Анализ идеи и зафиксированные assumptions

## 1. Краткий вывод

Идея сильная, потому что юнит в ней одновременно является работником, расходным ресурсом, испытуемым и будущей могилой, которая начинает кормить экономику. У игрока постоянно есть осмысленный выбор: оставить юнита работать, отправить в опасную локацию, использовать в лаборатории или рискнуть его lifetime ради более ценных предметов.

Главный риск — расползание систем. В идее уже есть магазин, кладбище, лаборатория, крафт, инвентарь, рецепты, пользовательские названия зелий, добывающие зоны, авторабота, урон, защиты, lifetime, дерево прокачки и ending. Поэтому MVP должен доказывать один полный цикл, а не пытаться сразу собрать много локаций.

## 2. Как использовать референс All Hail the Orb

Референс полезен не конкретными механиками, а структурой ощущения:

- компактная incremental-игра на одном экране;
- ручные клики в начале;
- постепенное превращение сцены в автоматизированную машину;
- новые системы открываются как награда за прогресс;
- странный, немного абсурдный, но не тяжёлый тон;
- конечная цель, после которой игра может завершиться.

Для Immortality Lab это означает:

- вместо культа — лаборатория бессмертия;
- вместо культистов — ассистенты/испытуемые;
- вместо devotion/power — Coins, Items, Potions, Experience;
- вместо комнат — локации на одной сцене;
- вместо орба — финальный протокол бессмертия.

## 3. Сильные стороны концепта

### 3.1 Смерть как полезное событие

Смерть не является fail state. Любая смерть создаёт могилу и выдаёт Experience по дизайнерскому правилу. Это делает даже неидеальные решения игрока частью прогресса.

### 3.2 Хорошая системная связка

```text
Добыча -> предметы -> крафт -> зелья / coal -> эксперименты или hazards -> смерть -> EXP + могила -> Coins -> покупка юнитов/upgrades -> новые локации и рецепты.
```

### 3.3 Крафт с безопасной ошибкой

Игрок может экспериментировать с ингредиентами. Если комбинация не задана геймдизайнером, игрок получает универсальный предмет `item_coal`, а не пустую ошибку. Coal можно использовать в будущих рецептах.

### 3.4 Пользовательские названия зелий

Игрок может дать новому зелью название и описание. Это создаёт личную историю прохождения, но не влияет на gameplay ID и не ломает save/load.

## 4. Главные риски и решения

### 4.1 Перегруз одного экрана

Риск: все локации, таймеры, иконки и юниты быстро делают сцену нечитаемой.

Решение:

- основная сцена показывает summary state каждой локации;
- детали открываются popup-ами;
- collectable-объекты видны прямо на локации;
- инвентарь, recipe book, upgrades и journal живут в popup.

### 4.2 Слишком много ручного клика

Риск: игрок обслуживает таймеры вместо принятия решений.

Решение:

- ручной сбор важен только в начале;
- авто-сбор через юнитов открывается рано;
- cemetery имеет storage cap, чтобы игрок не ловил каждый coin pickup;
- поздние локации требуют выбора assignment, а не постоянного клика.

### 4.3 XP-фарм может сломать баланс

Теперь любая смерть даёт Experience, поэтому игрок может попытаться фармить дешёвые смерти.

Решение:

- death EXP полностью настраивается геймдизайнером;
- lifetime death даёт низкое значение, например 1 EXP;
- дорогие potion deaths дают больше, но требуют item/potion затрат;
- upgrades могут иметь растущую стоимость;
- death reward rules можно балансировать по source, tier, location и potion.

### 4.4 Крафт может стать непонятным

Риск: игрок не понимает, почему одна комбинация дала зелье, а другая coal.

Решение:

- рецепты order-insensitive, но exact-match по набору и количеству;
- если игрок уже пробовал комбинацию, UI показывает known preview;
- unknown result показывается как полноценный результат “Уголь”, а не как ошибка;
- Recipe Book хранит tried recipes, включая failed recipes.

### 4.5 Юниты могут стать безликими

Риск: юниты будут восприниматься как батарейки.

Решение:

- минимум: имя, тип, портрет, короткая характеристика;
- средний уровень: traits, защиты, preferred locations;
- позднее: редкие юниты с особенными death interactions или work bonuses.

## 5. Зафиксированные assumptions

### 5.1 Валюты

- `Coins` — покупка юнитов, unlock локаций, казино, часть upgrades.
- `Experience` — валюта прокачки, выдаётся за каждую смерть по `DeathRewardRuleData`.
- `Items` — ингредиенты из локаций и крафта.
- `Potions` — крафтовые экспериментальные предметы, применяются в лаборатории и могут быть ингредиентами.

### 5.2 Experience

Каждая смерть выдаёт Experience. Runtime не должен проверять “новая ли смерть” перед выдачей base EXP.

Пример:

```text
lifetime_expired -> 1 EXP
potion_1_death -> 3 EXP
potion_4_death -> 5 EXP
radiation_hazard_death -> 2 EXP
```

First-time discovery bonus разрешён только как отдельное поле в authored data. По умолчанию core rule — EXP за каждую смерть.

### 5.3 DeathDiscovery

`DeathDiscovery` — это журнал и коллекция научных открытий. Он нужен для:

- энциклопедии смертей;
- силуэтов и подсказок;
- статистики;
- unlock conditions;
- ending grade;
- optional first-time bonus.

Но DeathDiscovery не является единственным источником Experience.

### 5.4 Крафт и coal

- Рецепты задаются геймдизайнером.
- Рецепт order-insensitive: учитываются IDs и quantities.
- Только exact authored recipe даёт настроенный output.
- Любая непреднастроенная комбинация даёт `item_coal`.
- `item_coal` универсален и не хранит recipe key внутри inventory stack.
- RecipeHistory может хранить recipe key -> `item_coal`, чтобы UI показывал preview при повторе.

### 5.5 Offline progress

Offline progress отсутствует. Закрытая игра не симулирует добычу, кладбище, смерть, lifetime, shop refresh или hazards.

### 5.6 Лаборатория

Если юнит помещён в слот лаборатории, он не теряет HP и lifetime, пока игрок не применит зелье или не уберёт юнита из слота.

### 5.7 Казино

Казино не наносит периодический урон и не влияет на lifetime. Каждый spin стоит Coins. Автоматизация casino worker-ом также должна платить Coins за каждый spin.

### 5.8 Конец игры

Игра заканчивается, когда игрок открывает финальный узел `immortality_final`. После этого на сцене появляется интерактивный объект. Клик запускает короткую сценку, титры и экран статистики.

## 6. Рекомендуемый MVP

MVP должен доказать один полный loop:

1. Игрок покупает юнита.
2. Отправляет юнита добывать предметы в первой безопасной локации.
3. Собирает предметы.
4. Варит зелье или получает `item_coal` из unknown recipe.
5. Помещает юнита в лабораторию.
6. Применяет зелье.
7. Юнит умирает.
8. Death pipeline выдаёт Experience по authored rule.
9. На кладбище появляется могила.
10. Могила создаёт coin collectable.
11. Игрок покупает первое upgrade.
12. Save/load корректно восстанавливает currencies, inventory, units, graves, timers и discoveries.
