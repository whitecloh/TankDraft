# Надёжность наград, покупок и прогресса
Status: решение владельца и исследование приняты; локальная реализация R3.2 проверяется; покупки ещё не реализованы
Last reviewed: 2026-09-15

## Приоритет и простой путь

Владелец попросил корректность в разумные сроки. Приоритет: оплаченный товар не теряется; неверное сохранение, сброс прогресса, ошибки входа и боя исправляются до расширения. В исключительном спорном случае допустима компенсация в пользу игрока. Это не разрешает клиенту повторно получать товар, выбирать сумму или заявлять о покупке без проверки.

Оставляем Fusion dedicated, Entity Objects/CAS и временный Legacy PlayFab. Не строим свою платёжную систему, распределённую транзакцию или второй кошелёк. Журнал завершённых результатов и обязанностей уже есть на backend; постоянные валюты и владение остаются в PlayFab. Azure, V2 billing и реальные покупки этим решением не включаются.

## Что подтверждают первичные источники

- [AWS: transactional outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html): бизнес-изменение и обязанность доставить событие сохраняются атомарно; получателю всё равно нужна защита от повторной обработки. Применяем принцип к нашему локальному журналу, AWS SDK не нужен.
- [PlayFab Server AddUserVirtualCurrency](https://learn.microsoft.com/en-us/rest/api/playfab/server/player-item-management/add-user-virtual-currency?view=playfab-rest): Legacy начисляет указанную сумму, возвращает баланс и изменение; idempotency key в контракте отсутствует. CustomTags — диагностические данные. Вывод для нашего адаптера: потерянный ответ не доказывает отказ.
- [PlayFab V2 idempotent transactions](https://learn.microsoft.com/en-us/gaming/playfab/economy-monetization/economy-v2/tutorials/idempotent-transactions-and-retries): IdempotencyId позволяет повторить ту же запись в пределах 14 дней; marketplace redeem защищён от повторного receipt. Это возможность будущего V2, её нельзя приписывать Legacy Add.
- [Unity IAP purchases](https://docs.unity.com/en-us/iap/purchases): pending может вернуться после перезапуска; ConfirmPurchase вызывается после устойчивой выдачи. Выполненные consumable покупки нужно учитывать удалённо, магазин не вернёт их как незавершённые.
- [Google Play security](https://developer.android.com/google/play/billing/security): backend проверяет purchaseToken, состояние PURCHASED, товар и привязку аккаунта; acknowledge/consume следует после выдачи. У Google неподтверждённая покупка может автоматически вернуться покупателю через три дня — нужна обработка на сервере, не только при следующем входе.
- [Legacy ValidateGooglePlayPurchase](https://learn.microsoft.com/en-us/rest/api/playfab/client/platform-specific-methods/validate-google-play-purchase?view=playfab-rest): PlayFab проверяет receipt и выдаёт сопоставленный catalog item; один receipt используется один раз. ReceiptAlreadyUsed сам по себе не доказывает право текущего аккаунта: обязательна проверка привязки/предыдущего исполнения. Совместимость конкретной версии Unity IAP/receipt и настроек магазина проверяется в sandbox перед выбором окончательного адаптера.
- [PlayFab SetObjects](https://learn.microsoft.com/en-us/rest/api/playfab/data/object/set-objects?view=playfab-rest): ExpectedProfileVersion предназначен для контроля конкурентной записи. Сохраняем уже реализованный CAS, вместо безусловной перезаписи профиля.

## Текущие боевые награды — R3.2

1. Результат и обязанность перед каждым человеком фиксируются до показа итогового результата. Сетевой клиент не может создать такую обязанность.
2. Чтение баланса перед Legacy Add повторяется максимум три раза с паузами 250/750 мс; после успешного чтения выполняется одна попытка Add. Ошибка после начала Add никогда не запускает автоматический повтор. Исчерпанные чтения тоже сохраняют обязанность для разбора, не теряют её и не создают бесконечный поток запросов.
3. Успешный ответ проверяется по account/currency/BalanceChange и диапазону баланса. Равенство с ранее прочитанным глобальным балансом не требуется: параллельная корректная операция или задержка чтения не должны создавать ложную неопределённость.
4. NeedsReview разбирается локальным оператором. `ConfirmApplied` допускается только при независимом подтверждении операции с тем же результатом, игроком и суммой; в журнале остаётся ссылка на доказательство. Одного сравнения баланса недостаточно. Утилита не проверяет доказательство за оператора.
5. Когда доказательства нет, для малой тестовой награды можно выбрать `CompensateOnce`. Это явно разрешённая компенсационная попытка, а не заявление о неисполнении первой операции. Максимум одна такая попытка на обязанность, решение и прежняя причина сохраняются. Если первая выдача состоялась, игрок может получить двойную сумму. Повтор команды/restart не создаёт третью выдачу. Повторная неопределённость остаётся видимой для поддержки; без подтверждения не объявляем успех.

Текущий предел — 10 обычных наград по 1 CO на аккаунт; компенсация может добавить ещё до одной такой суммы для каждой спорной обязанности, то есть верхняя граница до 20 CO. Это граница тестовой внутриигровой выдачи, не гарантия бесплатности произвольного количества API запросов. Автоматические начисления денег, премиальной валюты или покупки этим механизмом не разрешаются.

## Магазин — контракт следующих этапов, не выполненная интеграция

Для IAP используем Unity IAP pending/confirm и готовую проверку/выдачу у провайдера, где поддерживается нужный магазин и receipt. Проверяем bundle/package, product/quantity, account binding, transaction token и состояние оплаты. Один платёж привязывается к одному аккаунту и одной сохранённой обязанности. Цена, содержимое набора и права вычисляются доверенным backend/каталогом, клиент сообщает намерение и receipt.

Выдача сохраняется до подтверждения магазину; повтор после потери ответа возвращает прежний результат. Не подтверждаем покупку по клику, локальному флагу или только успешной валидации без факта выдачи. Обрабатываем незавершённые покупки после запуска/переподключения и через серверные уведомления; deferred/pending payment ещё не оплачены. Редкая поддержка/компенсация возможна только после проверки платежа; автоматическое повторное списание запрещено. Если выдача пока недоступна, долг виден и восстанавливается, либо платёж возвращается — не показываем ложное «выдано».

Для покупок за игровую валюту предпочитаем одну поддерживаемую провайдером операцию списания+выдачи. Не делаем клиентское Subtract, затем независимый Grant. Если Legacy не обеспечивает нужную операцию улучшения, перед R3.3 отдельно фиксируем небольшой восстанавливаемый workflow или ограничиваем конкретный тестовый товар; не объявляем две записи атомарными. При неопределённости повторное списание не допускается.

До настоящих платежей обязательны sandbox: повтор callback, подмена receipt/товара/аккаунта, оплачено→закрытие игры, выдано→потерян ответ, restart до confirm, restore, refunds/revocation. Покупки должны оставаться доступными для восстановления после простоя игрового сервера; ПК разработчика не является релизной гарантией доступности. Современный Apple StoreKit 2 требует отдельной проверки серверного signed transaction, поддержка Legacy Google не означает поддержку всех платформ.

## Прогресс, вход и бой

Ошибка чтения/таймаут/повреждённый объект — ошибка загрузки, а не новый игрок. Не записываем значения по умолчанию вместо недоступного профиля. Новый профиль допустим только при подтверждённом отсутствии именованного объекта и через CAS. CAS conflict требует перечитать данные; старый клиент не может перезаписать свежий прогресс. Повтор одной команды сохраняет operation ID и payload; потерянный ответ после записи разрешается чтением, а не сбросом. Эти условия покрываются регрессионными тестами в текущем патче.

Результат боя определяет сервер. Отключение клиента не должно выдавать результат или награду повторно. Завершённые результаты сохранены локально; потеря диска и восстановление незавершённого боя после потери authority остаются отдельными задачами R2/эксплуатации. Перед ценной экономикой нужны проверенный backup/restore, durable hosting, безопасная привязка аккаунта и закрытие auth/reconnect критичных багов. Это реальные оставшиеся работы, а не обещание отсутствия любых ошибок.

## Следующий шаг

Закончить локальные проверки процедуры R3.2 и перейти к R3.3: показать ожидающую/выданную награду, перечитать профиль/баланс, улучшить или сменить армию, начать следующий матч. Не задерживать основной цикл разработкой автоматической сверки всех Legacy операций или собственной платёжной платформы.
