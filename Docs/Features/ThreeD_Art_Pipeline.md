## Что сохраняем

Читаемая портретная арена, вид сверху под небольшим углом, крупные силуэты, короткие корпуса, заметные башни/стволы, минимум мелкой фактуры. Молочно-светлые поверхности, чёрный контур и цветные метки команды. Массовые бои важнее реалистичности одного танка. UI остаётся плоским и близким референсу.

Боевой LeoECS-контракт и движение остаются двумерными; только presentation отображает координаты поля на X/Z в 3D. Высота полёта/дуга снаряда визуальны, а возможность поражения воздушной цели — отдельное правило domain. Переход не требует синхронизировать PhysX или вычислять попадания по мешам.

## Рекомендуемый производственный путь

1. Утвердить один кадр с игровой камеры и силуэты тяжёлого танка, ПТ, артиллерии и инженера. Ориентир — утверждённый A1. Проверить также вариант без сильного наклона камеры: перспективное сжатие задних рядов может мешать чтению боя.
2. Для первого танка сделать согласованные front/side/top и 3/4. Генерация может давать противоречащие виды, поэтому размеры и расположение деталей нужно выверять перед моделированием.
3. Собрать в Blender настоящую low-poly модель из модулей: корпус, гусеницы, башня, ствол, 1–2 ролевых элемента. Шаблон модулей позволит быстро выпускать средний/лёгкий/тяжёлый варианты. Сложным героям нужны собственные силуэты.
4. Настроить pivots, масштаб, UV, общую палитру/атлас и простые материалы. Башня вращается отдельно, ствол откатывается, корпус слегка реагирует на выстрел; для механики достаточно rigid transforms. Мелкие винты/траки лучше запечь или опустить.
5. Экспортировать FBX в Unity, сохранить исходник Blender отдельно, проверить ориентацию, root scale, anchors Muzzle/Hit, тень и размер относительно игрового радиуса. Authored prefab/pool сохраняет stable content ID.
6. Получать UI PNG/иконки **из утверждённой 3D-модели** с фиксированным светом и камерой. Тогда коллекция и бой показывают одну технику. Вырезанные из concept PNG подходят как reference/placeholder, но не гарантируют форму невидимой стороны.
7. Проверить один готовый комплект в отдельной 3D test scene, включая плотную армию, размеры юнитов на экране, стрелки/снаряды/лужи. Только после визуального сравнения переводить всю арену и масштабировать контент.

Автоматизация Blender полезна для повторяемых корпусов, UV палитры, pivot/export validation и batch render иконок. Она не заменяет проверку силуэта и аккуратной модели. В текущей среде Blender не обнаружен; фактическая сборка/экспорт модели в этом аудите не выполнялись.

## Почему PNG → 3D не является точной конвертацией

Blender Images as Planes создаёт плоскость с изображением. Для декора/иконки это удобно, но объёма корпуса и правильного вращения башни не появляется. [Blender manual](https://docs.blender.org/manual/nb/5.0/modeling/meshes/import_images_as_planes.html).

Image-to-3D можно использовать для черновика. Например, Meshy принимает несколько согласованных ракурсов (1–4); результат всё равно нужно проверять по topology, деталям, материалам и разделению движущихся частей. Бесплатность/лицензия/коммерческие права конкретного сервиса проверяются перед использованием; API и платные операции не включены. [Meshy multi-image API](https://docs.meshy.ai/en/api/multi-image-to-3d).

Для нашей стилизованной техники ручная или параметрическая сборка простых модулей обычно даёт больше контроля над силуэтом и бюджетом, чем очистка случайной плотной сетки. Это инженерная рекомендация под проект, не универсальный результат benchmark.

## Начальные ограничения для пробного ассета

Начальные, пересматриваемые после профилирования ориентиры: примерно 500–1500 треугольников на обычную машину, до 2000 на крупную; общий палитровый атлас, один основной материал, несколько отдельных transform для башни/ствола. Это не норматив Unity и не обещание FPS. При маленьком экранном размере избыточная геометрия не улучшает читаемость. Уровни детализации, instancing и тени выбираются после профиля, с учётом будущего WebGL.

Unity рекомендует ограничивать геометрию, материалы и сложность рига исходя из платформы и экранного размера; batching зависит от render pipeline и повторного использования материалов. [Оптимизация моделей](https://docs.unity3d.com/kr/6000.0/Manual/ModelingOptimizedCharacters.html), [выбор оптимизации draw calls](https://docs.unity3d.com/jp/current/Manual/optimizing-draw-calls-choose-method.html).

## Критерии решения о переходе

- Владелец принимает вид **реальной** тестовой сцены с игровой камеры, а не только concept.
- Синие/красные ряды, типы техники и главные способности читаются без приближения.
- Плотный бой укладывается в измеренные CPU/GPU/memory бюджеты; нет материала на каждую машину и скрытого размножения текстур.
- 2D→3D view mapping не меняет seed, урон, движение и серверные результаты.
- UI совпадает по поведению с reference-аудитом; камера и материалы не требуют переделки прогрессии/сохранений.

После одобрения направления следующий шаг — один модельный танк, одна ПТ/турель и тестовая 3D-арена. Массовая генерация всех моделей до этой проверки нецелесообразна.
