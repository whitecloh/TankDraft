## Целевой flow

1. Клиент проходит PlayFab authentication; сервер проверяет ticket, сам назначает account/side и сверяет запрошенный MatchId с серверным назначением.
2. Authenticated queue ждёт до 10 секунд. При отсутствии второго человека server назначает bot fallback; его текущие действия — server autochoices по draft deadline 5 секунд, как для disconnected player. Think-policy и подбор силы из local coordinator ещё не перенесены.
3. Один bounded RemoteHost process создаёт trusted assignment с content version, сторонами и уникальным server instance ID. Assignment не переносится между instances.
4. `MatchAdmissionService` выдаёт short-lived match access; клиент открывает WSS только с этим access.
5. Authoritative server продолжает симуляцию при disconnect одного или обоих клиентов. Reconnect повторно проверяет PlayFab ticket и использует действующее assignment/access flow.
6. Нормально завершённый match удерживает authoritative result в памяти 120 секунд только для показа и requeue. Ни рейтинг, ни награда, ни другая durable mutation в этом slice не выполняются.

## Потеря instance

Если Edgegap container остановлен, уничтожен или server instance ID истёк, каждый незавершённый match становится `void`. Мёртвый server не может уведомить клиентов; только новый authenticated request с прежним значением поля `InstanceId` получает `409 InstanceExpired`. RemoteQueueClient очищает старое назначение при 409 и показывает причину. В Windows QA endpoint задаётся оператором; автоматическое обнаружение нового deployment и выход из боя при полной потере instance пока требуют отдельной реализации. Старый match не восстанавливается на новом container. Restart теряет все in-process results, поэтому текущий slice не заявляет переживание результатов после container loss.

Будущая release durability требует external idempotent commit, fencing и recovery. До их реализации нельзя объявлять рейтинг, награды или final result переживающими restart/container loss.
