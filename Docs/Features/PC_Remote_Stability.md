# Проверка повторных удалённых матчей на ПК
Status: two cloud Human matches and both-client socket outage PASS; rare response-wait stalls remain
Last reviewed: 2026-09-14

Владелец утвердил следующий этап на ПК. Серверные сценарии проверяем двумя Windows Player; Android остаётся отдельной проверкой производительности, lifecycle и мобильного маршрута. Условие текущего удалённого этапа — рабочий VPN. PlayFab + Edgegap, временно без Azure; экономика выключена. Этот патч не закрывает production durability и мобильную приёмку.

## Изменения

- `ServerClientTransport` сохраняет метрики обмена вместе с полученным кадром. Раньше `LastPollMs` мог относиться к следующему запросу, а не к отображаемому snapshot. `ReceivedServerFrame` теперь несёт timestamps, payload size, connection, access generation, stream и последнее успешное renewal time.
- `ServerClientSession` пишет `DiagnosticsVersion=2` и `MatchId`. `SendMs` измеряет отправку; `ResponseWaitMs` — время после отправки до полного ответа, включая ожидание сервера и транспорт; это не чистый сетевой RTT. `JsonDecodeMs` измеряет JSON parsing, `SnapshotDecodeMs` — последующую обработку до постановки кадра в очередь, `PresentationAgeMs` — возраст кадра при отображении. Connected/Pending относятся к моменту отображения.
- Исправлена воспроизведённая ошибка повторного боя: один `intent-{side}.json` сохранял StreamId первого матча и отклонял второй. Remote-журнал теперь имеет имя `intent-{side}-{sha256(matchId)}.json`. Возврат в тот же матч сохраняет pending operation/sequence; чужой stream по-прежнему отклоняется. Старые QA-журналы не удаляются и не импортируются: обновление клиента посреди незавершённого матча со старым форматом не проверено и не является миграцией production-сохранений.
- `run-remote-clients.ps1 -Players 2 -Matches 2 -DisconnectLastMatch` запускает ограниченный сценарий: результат → меню → очередь → новый матч. Во втором матче каждый клиент один раз прерывает сокет на 40 секунд. Это не завершение процесса и не потеря VM. Сервер продолжает жить. По умолчанию автоматический запуск остаётся на один матч, fault выключен.
- Assignment history и fault timestamps записываются отдельно. `verify-remote-pc-run.ps1` требует два разных Human-матча на одной instance, противоположные стороны, результаты обоих клиентов, одинаковый счёт и entity hashes общих battle ticks, возвращение после заданного обрыва. Cadence считается внутри раунда и одного соединения. PASS не доказывает отсутствие любых задержек; метрики требуют анализа.

## Проверено локально

- ServerClient: **77/77 PASS**, `Logs/VpnQa/pc-stability-client-final.trx`. Есть проверка неизменности метрик buffered frame после renewal, медленного TLS ответа, отдельного журнала нового матча и сохранения pending после потерянного ACK.
- Ошибка журнала сначала воспроизведена: `Logs/VpnQa/pc-repeat-journal-before.trx` — ожидаемый failed regression. После исправления: `pc-repeat-journal-fixed.trx`, 77/77 PASS.
- RemoteHost: **35/35 PASS**. Реальные HTTP/WebSocket loopback integration tests с тестовым identity verifier: два матча одних игроков; потеря ACK и повтор без второго применения; обе стороны offline до результата и одинаковый результат после возврата; точная граница драфта 5 секунд; изменённый payload того же operation и устаревший выбор отклоняются. Это не cloud PlayFab тест.
- Windows QueueMenu Player собран через открытый Unity Editor/MCP: `Logs/BackendClient/build-status.txt` — Succeeded, 0 errors, 0 warnings. Сам Player с этим патчем в облаке ещё не запускался.
- PowerShell launcher разобран без syntax errors; verifier прошёл синтетические проверки корректной пары, отказа при разных hashes и отсутствующем результате. Синтетические данные помечены и не являются runtime evidence.

## Следующий ограниченный облачный прогон

1. Один подтверждённый Free Tier deployment существующего server image `remote-f13754c37640`, 0.5 vCPU / 1 GiB, максимум 15 минут. Серверный runtime этим патчем не изменён. Использовать прежние две тестовые PlayFab identity, без экономики.
2. Проверить readiness/TLS/content, запустить новую ПК-сборку указанным сценарием. Убедиться, что оба назначения Human, а не Bot fallback.
3. Дождаться обоих результатов двух матчей; выполнить verifier, отдельно разобрать интервалы кадров и причины пауз по метрикам v2. При отказе сохранить evidence и не объявлять приёмку.
4. Завершить test processes, убрать приватные bootstrap и остановить deployment с подтверждением состояния провайдера.

## Облачный прогон 14.09.2026

Deployment `76f119710450`, Frankfurt, Free Tier 0.5 vCPU / 1 GiB; существующий server image, прежние две PlayFab QA identity, экономика выключена. Evidence: `Logs/RemoteClient/b2f9de51935947d3882e3e36b7b09a6c/verification.json`, `cadence-analysis.json`; manifest — `Logs/VpnQa/cloud-76f119710450/manifest.json`. Два Windows Player на одном ПК; самостоятельного подтверждения VPN-состояния ОС не выполняли, настройки маршрута не меняли. Это не проверка независимых сетей или Android.

Verifier: **PASS** для указанного ограниченного сценария. Оба клиента завершились автоматически; два временных private bootstrap удалены. При первом запуске найден и исправлен конфликт `$Matches` со служебной regex-переменной PowerShell: параметр теперь `$MatchCount`, прежний switch `-Matches` сохранён alias. Исправленный launcher реально запустил оба клиента.

Остановка: Edgegap UI подтвердил `Terminated`; создание 10:02:00 UTC, запрос остановки обработан 10:07:38 UTC, в пределах согласованных 15 минут. Платный режим не включался.

Интервалы отображения полученных battle snapshots (внутри раунда/соединения, без планового обрыва): медиана около 100 ms; p95 по четырём выборкам 117.140–150.299 ms; максимумы 366.678–683.088 ms. Из 2380 интервалов 16 превышают 300 ms. Это cadence snapshots, не FPS и не задержка от ввода до сервера.

Максимальная пауза 683.088 ms: ResponseWaitMs=675.468, JSON=3.155 ms, snapshot conversion=0.128 ms, Unity frame около 16.667 ms, generation остаётся 2. Другая пауза 633.558 ms соответствует ResponseWaitMs=624.591 при неизменной generation. Следовательно, эти паузы локализованы в ожидании ответа после отправки, а не в этих измеренных стадиях parsing/presentation или renewal. Метрика включает маршрут, серверную обработку и ожидание транспорта; объявлять причиной только VPN либо только сервер нельзя. Полная плавность ещё не принята.

Следующий патч: измерение времени обработки Poll на сервере и очередей отправки, сопоставление с timing клиента; затем уменьшение подтверждённого источника пауз без ослабления authority/TLS/валидации и без увеличения постоянной задержки отображения вслепую. Отдельно остаётся kill/relaunch с pending command и потерянным ACK в облаке (локальный lost-ACK integration test уже есть).

Пока не проверены этим патчем: kill/relaunch клиента, мобильный lifecycle, независимые сети, нагрузка, восстановление после потери контейнера и ровно однократная выдача награды. Предыдущий успешный PC/Android VPN матч и PC-пауза 433 ms описаны в [VPN_QA_Stabilization.md](VPN_QA_Stabilization.md); причину старой паузы ретроспективно установить нельзя.
