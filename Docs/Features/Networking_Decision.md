## Новое требование владельца: доверенный server authority

Зафиксировано 2026-09-13. Доверенный сервер валидирует client decisions и владеет таймерами, симуляцией и результатами. Он продолжает матч при отсутствии одного или обоих игроков и при каждом пропущенном выборе применяет случайное допустимое усиление, в том числе через несколько пропущенных раундов. Возврат по устойчивой идентичности восстанавливает актуальные фазу, армию, счёт или итог без просмотра пропущенных боёв. Это supersedes prototype pause behavior; текущий runtime не мигрирован.

[Server_Authority_Architecture.md](Server_Authority_Architecture.md) содержит требования к authority. Владелец 2026-09-13 выбрал попробовать PlayFab Multiplayer Servers для dedicated hosting и PlayFab + Azure для мета-сервисов; transport и конкретные версии фиксируются только после spike. PUN 2 не заменяется и SDK не меняется этим решением. Детали — [PlayFab_Azure_Stack.md](PlayFab_Azure_Stack.md). Вероятность выбора, длительности таймеров, fairness при сбое сервера и auto-surrender здесь не определяются.

[Networking_Stack_Comparison.md](Networking_Stack_Comparison.md) сохраняет историческое сравнение Unity NGO/NFE, Mirror, FishNet, Fusion и C# server, включая бюджет тестов 20–100 CCU. Решение о PlayFab MPS/PlayFab+Azure не является выбором Mirror, PUN или другого transport; SDK/runtime не мигрированы.

Для раундового драфта передавать команды выбора/готовности, версию контента, seed и проверенные результаты/снапшоты. Не создавать PhotonView на каждую мину/пулю без доказанной нужды.
Синхронизация должна охватывать весь ход боя, а не только стартовый seed и финальный исход. Предлагаемая схема, контракт команд/состояния и критерии проверки приведены ниже; выбранный PUN SDK сам по себе этот контракт не реализует.
Вариант PUN 2: transport adapter + отдельный backend, который выдаёт/проверяет легальные офферы, фиксирует команды, считает или воспроизводит исход и единожды выдаёт награду. Одна сверка присланных клиентами хешей не защищает от сговора.
Вариант нового Photon-проекта: Fusion 2 с Server Mode; требуется собственный headless hosting, Photon не предоставляет его автоматически: https://doc.photonengine.com/fusion/v2/concepts-and-patterns/dedicated-server-overview .
Альтернатива для pure C# ECS: собственный match service с командами и снапшотами; транспорт выбирается по задержке, нагрузке, эксплуатации и стоимости, а не по числу игровых объектов.

Рекомендация: до final SDK lock сделать маленький двухклиентный сетевой spike с deadline, reconnect, дубликатами команд, headless round simulation. PUN 2 пригоден как транспорт, но не считать его полным backend.
Для подключения PUN нужны официальный SDK и Photon Realtime AppId для TankDraft. Не переносить чужой AppId; не создавать платные сервисы без явной команды.

SDK PUN 2.50 импортирован из локального официального Asset Store cache, core сборки компилируются в Unity 6.3. Владелец настроил AppId; локальное хранение и диагностический transport probe реализованы. Два отдельных Windows Player-клиента успешно проверили реальный Photon Cloud, общую комнату, 20 request/ack и Disconnect → ReconnectAndRejoin с прежним actor ID. Инструкции и evidence — Photon_Setup.md. Network match prototype с pinned authority, snapshots, command identity и diagnostic launcher прошёл Unity authoring/build, два Windows-клиента и Editor с внешним guest. Проверены полный матч, rejoin и восстановление снимков; широкая матрица плохой сети и доверенная server topology остаются открытыми. См. Network_Match_Prototype.md.

## Требование владельца: согласованный ход боя

Зафиксировано 2026-09-12. Для одного simulation tick оба клиента должны получать одинаковые игровые состояния и события: stable entity ID, позиции, цели, начало атаки, создание/попадание снаряда, создание/тики зоны, HP, смерть, spawn и outcome. Смена ориентации арены под своего игрока — преобразование presentation, а не изменение симуляции. Render FPS, разрешение и косметические частицы не обязаны совпадать попиксельно, но не могут менять действия юнитов или скрывать/создавать боевые события.

Абсолютную одновременность физических экранов при произвольном качестве связи не обещаем. Используем общую временную шкалу и буфер отображения; измеряем разницу показанных ticks и задержку. При нехватке данных клиент явно переходит в восстановление синхронизации, а не продолжает выдумывать попадания/смерти/результат.

## Предлагаемая основа первого сетевого прототипа

Один authority продвигает текущую fixed-step симуляцию LeoECS Lite и принимает команды обоих игроков. Для релиза рекомендуется доверенный match service, который считает бой по ходу времени и выдаёт состояния/события. Сервис, лишь проверяющий итог после боя, сам по себе не обеспечивает совпадение видимого хода. Конкретное размещение сервиса и его связь с PUN остаются предметом spike; live-инфраструктура не создаётся этим документом.

- Команды содержат actor/sequence/match/round/content version; authority назначает принятый simulation tick и возвращает подтверждение. Клиентский timestamp не даёт права применить команду задним числом. Будущие действия во время боя проходят тот же путь; в spike проверить внедрение команды посреди боя через QA-вход, не расширяя этим production UI.
- Пакеты состояния несут match/round, authority epoch, tick, sequence и, для дельты, baseline ID. События имеют устойчивый ID и simulation time. Получатель отбрасывает старые/чужие пакеты и дубликаты, восстанавливает пропуски; события и снапшоты согласованы по tick, чтобы попадание не показывалось дважды или после неверного despawn.
- Клиенты буферизуют подтверждённые состояния на общей шкале времени и плавно отображают позиции/повороты между ними. Выбор целей, раздвижение, урон и исход не рассчитываются независимо Unity-физикой на двух телефонах. Скорость анимации/FPS не являются часами симуляции.
- Движение может передаваться компактными состояниями/дельтами, а атаки, spawn/death и прочие значимые события должны восстанавливаться без потерь. Способ доставки выбирается в transport adapter с учётом семантики, а не правилом «всё reliable». Частоты simulation/network/render независимы; их значения и буфер определяются замерами.
- Reconnect использует полный актуальный snapshot с watermark событий и дальнейший поток; не требует проиграть весь бой с начала. Повторная доставка не повторяет эффект/смерть/награду. Замена authority требует отдельного протокола epoch и восстановления, а не автоматического доверия новому MasterClient.
- Outcome использует точнейшее simulation time попаданий/смертей. Если последние армии уничтожены на точно одном времени, pinned authority ровно один раз применяет seeded random tie-break, включает winner и seed trace в общий state/result и не поручает клиентам локальный roll.

Локальный core сохраняет воспроизводимость для тестов и replay. Seed-only lockstep двух устройств не принимается как доказанная замена потока authority: сначала нужны доказательства межплатформенной детерминированности и определённая политика поздних команд/восстановления. PUN 2 не подменяется другим SDK без отдельного решения.

## Критерии ранней проверки

Проверить на двух отдельных клиентах ещё с prefab-примитивами. Предлагаемая тестовая матрица, а не обещанные эксплуатационные пределы: RTT 50/150/300 ms, jitter до 50 ms, потери 0/1/5%, дубликаты/перестановка пакетов, FPS 30/60 и краткое зависание одного клиента; затем background/reconnect. Windows-проверка не заменяет Android/iOS.

Для одного подтверждённого tick должны совпасть нормализованное восстановленное состояние, список принятых команд и упорядоченный журнал значимых событий; пропуски, повторные смерти или разный outcome недопустимы. Сверять одинаковую версию и точность сетевого представления, а не сравнивать байты float simulation со сжатым wire state. Снимать совместное видео и метрики: разница presentation ticks, p95/p99 задержки событий, остановки буфера, коррекции позиций, трафик и стоимость обработки при максимальном числе юнитов/снарядов прототипа. Численные пороги плавности/задержки утвердить по результатам spike; статус «синхронизация проверена» до этого не ставить.
