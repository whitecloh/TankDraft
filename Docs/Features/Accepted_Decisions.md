# Принятые решения

Актуальное решение владельца 15.09.2026: работа идёт в трёх этапах. Сначала на PC завершается полный клиентский цикл: все окна, механики и функциональные анимации; authored configs → data/services → presenters/views; prepared prefabs и LayoutGroups, без ожидания финального арта. Затем завершается PlayFab + Photon Fusion Dedicated server: тестовый сервер на ПК, сохранения, экономика, покупки, безопасность и recovery. После этого Unity WebGL + Playgama Bridge подключается к Яндекс Играм как первой внешней тестовой площадке с авторизацией, рекламой, покупками и браузерной приёмкой. Клиент учитывает действующие серверные контракты и WebGL-ограничения, но не становится authority; существующая серверная реализация сохраняется. VK и Android/iOS не являются ближайшими этапами. Платформенные SDK пока не устанавливались и не проверялись. Legacy Catalog/Inventory/Currency остаются временным QA-provider, профиль — Entity Objects, Azure выключен; billing, live grants и иные платные/live изменения этим решением не разрешены. Единый подробный план: [Functional_Release_Plan.md](Functional_Release_Plan.md). Старые приоритеты ниже носят исторический характер.

Актуальное решение владельца 14.09.2026: Photon Fusion 2 Dedicated Server, тестовый server process на ПК владельца, PlayFab для меты. Утверждены миграция SDK и удаление неиспользуемого стека. План: [Fusion_Dedicated_Migration.md](Fusion_Dedicated_Migration.md). Server authority, offline autochoice, reconnect и LeoECS остаются обязательными. Старые записи Edgegap/PUN ниже — история, не разрешение переключать актуальное направление обратно.

- Историческое решение владельца 14.09.2026: пользовательские сохранения — PlayFab Entity Objects, владение/валюты/инвентарь — Economy V2 Inventory, магазин/цены — Economy V2 Catalog + Stores, баланс — TitleData/Internal TitleData, IAP — Unity IAP + PlayFab redemption. Оно заменено для текущего бесплатного QA временным Legacy Catalog/Inventory/Currency и Entity Objects для профиля; WebGL-платформенные IAP будут проектироваться на третьем этапе через проверяемый серверный контракт, а не включаться сейчас. Azure не возвращаем; данные пишет доверенный backend; ledger/однократная награда и восстановление боя требуют отдельной реализации. Контракт: PlayFab_Player_Data_Design.md. Обсуждение PUN 2 не является решением сменить действующий сетевой стек.

- Полный флоу Draft Showdown, второй видеореференс приоритетнее первого.
- Портретная мобильная игра, 4 типа техники в колоде, множество экземпляров, заклинания/приказы.
- Бой до 4 выигранных раундов; проигравший получает камбэк-усиление.
- Боевую фазу длительностью около минуты или меньше обеспечивать настройками баланса. Не вводить отдельный игровой таймаут, овертайм, урон от поля или сравнение HP по истечении минуты (уточнение владельца 2026-09-12).
- Результат боя фиксируется по точнейшему времени попаданий/смертей. При точной одновременной гибели последних армий authority один раз выбирает seeded random winner и передаёт общий результат вместе с seed trace; локальный клиент не выполняет свой roll.
- Первый боевой прототип — на примитивах, включая различимые юниты, летящие снаряды, попадания и зоны периодического урона. Заранее подготовленные view-prefabs должны допускать быструю замену арта без изменения боевой логики.
- Сохранять возможность будущих действий игрока во время боя: runtime должен принимать команды в ходе симуляции. Предварительно рассчитанное воспроизведение всего боя не является обязательной моделью gameplay.
- Настоящий PvP в релизе обязателен; боты обязательны для доступного матча при малом онлайне.
- Оба игрока должны видеть согласованный ход боя: те же перемещения и цели юнитов, выстрелы, попадания, зоны, смерти и результат. Проверять синхронизацию двух клиентов с сетевыми задержками и разным FPS уже на примитивах; одинаковый итог без одинакового хода боя недостаточен. Конкретные критерии и предлагаемая схема — Networking_Decision.md.
- Решение владельца от 2026-09-13: доверенный сервер валидирует решения клиентов, владеет таймерами, симуляцией и результатами. Матч продолжает идти при отсутствии одного или обоих игроков; при каждом пропущенном выборе сервер применяет случайное допустимое усиление, включая несколько пропущенных раундов. Возврат по устойчивой идентичности восстанавливает текущие фазу, армию, счёт или итог без просмотра пропущенных боёв. LocalOnly authoritative runtime, очередь и reconnect реализованы и проверены на Windows/Android USB; production identity, remote host и distributed recovery остаются впереди. PauseProcessDowntime — только QA-политика локального persistence adapter.
- Решение владельца от 2026-09-13: попробовать PlayFab Multiplayer Servers для dedicated hosting. PlayFab + Azure выбраны для аккаунтов, сохранений, экономики и покупок по инфраструктурному подходу Chibi Arena. Матчевый transport и live provisioning проверяются отдельно; целевой stack — [PlayFab_Azure_Stack.md](PlayFab_Azure_Stack.md). По последующему поручению установлены Unity/API/GSDK зависимости без login/облачного запуска: [PlayFab_SDK_Setup.md](PlayFab_SDK_Setup.md).
- Актуальное решение владельца 2026-09-13: реализовать PlayFab/Azure/Edgegap и первые тесты; обновить план в памяти. Edgegap Free Tier выбран для тестового dedicated compute. Предыдущая попытка Oracle остановилась на недоступной регистрации; PUN host migration обсуждался как гипотеза, но не является текущим направлением. Сервер продолжает матч при отсутствии обоих игроков; отмена обоим из PUN-гипотезы не переносится. 10–20 одновременных матчей — цель замера, не доказанная ёмкость. Нулевые расходы остаются обязательны; MPS не активируется, LocalHost с QA grants не публикуется. Детали: [Edgegap_Integration.md](Edgegap_Integration.md).
- Решение владельца от 2026-09-13: начать серверную реализацию с защитой взаимодействий и исключением платежей на первых этапах. Текущий разрешённый режим — LocalOnly; облачный запуск не выполняется без доказанного принудительного ограничения со стороны провайдера. Budget/уведомления и included free quota не дают такой гарантии. S1/S2/S3 реализованы локально, включая SQLite recovery и outbox с test ledger; этапы и критерии — [Backend_Implementation_Plan.md](Backend_Implementation_Plan.md). PauseProcessDowntime в S3 — техническая политика QA, не решение владельца о release-компенсации серверного простоя.
- Временное решение владельца от 2026-09-13: R1 remote prototype не использует Azure. PlayFab identity остаётся источником authenticated account, Edgegap запускает один bounded authoritative process для очереди и матчей. После disconnect сервер продолжает матч; потеря container/instance немедленно истекает и voids незавершённый match без рейтинга, награды или иной live economy mutation. У процесса есть уникальный instance ID, поэтому stale match не возобновляется на новом instance. RemoteHost локально проверен, но remote PvP не принят. Durable backend сохраняется будущим направлением: результаты нельзя объявлять переживающими container loss до внешнего идемпотентного commit: [Edgegap_NoAzure_Prototype.md](Edgegap_NoAzure_Prototype.md).
- Для временного R1 bot fallback после 10-секундной очереди использует только server autochoices по draft deadline 20 секунд, как disconnected player. Адаптивная think-policy и подбор силы bot из local coordinator не перенесены; они остаются требованием последующей release-приёмки.
- Контент и мета: коллекция/редкости/уровни/мастерство, арены, командир, награды/паки, магазин/IAP/rewarded ads, пропуск, рейтинг, профиль/косметика/настройки.
- Техника от начала 1900-х до современных машин/средств. World of Tanks — ориентир классов. Игровые роли и эффекты переносить из референса.
- Ряды от переднего к заднему: ловушки/мины/ежи → тяжёлые/средние танки → ПТ/точечные дальние атаки → САУ/площадной урон/спавнеры. Специальные рейдеры обходят/попадают в тыл; инженер поддерживает/призывает.
- Роли не смешивать в произвольной толпе при расстановке; специальные перемещения — явные механики.
- Odin не использовать. LeoECS Lite — выбранная основа боевого runtime.
- Пользователь уточнил Photon2 = PUN 2. Ограничения и финальная серверная схема описываются отдельно; не менять SDK молча.
- Authoring через конфиги и подготовленные prefabs; runtime не конструирует production-иерархии с нуля.
- Документы ImmortalityLab устарели и не задают правила TankDraft.
- Порядок: документы/Codex → MCP → необходимые пакеты и setup → план архитектуры/экранов → инструмент превизов → вёрстка через MCP → реализация фич.

Декомпозиция и критерии этапов: [Functional_Release_Plan.md](Functional_Release_Plan.md); старый bootstrap порядок: [Delivery_Sequence.md](Delivery_Sequence.md). - Повторяющиеся UI-объекты одинакового назначения размещаются общим authored prefab и LayoutGroup с едиными размерами, отступами и центровкой; отдельная ручная настройка sibling допускается только как явно authored исключение.
