# План дальнейшей разработки
Status: local full match implemented; network match prototype passed initial Windows/Editor validation; release scope remains
Last reviewed: 2026-09-13

## Зафиксированная база

Этот план не пересматривает уже принятые требования: portrait Draft Showdown, четыре типа техники и четыре победы в матче, реальные PvP и боты при низком онлайне, полная мета в релизе, LeoECS Lite для боевого runtime, authored configs и подготовленные prefabs, запрет Odin. Роли и начальные ряды также приняты: преграды → танки → ПТ → САУ, а flank/рейдеры и инженер остаются явными специальными механиками.

Сейчас реализован local main-menu runtime slice: immutable profile/meta contracts, authored configs, strict local save, VContainer startup, presenter и flow коллекции с заменой слота. `ProfileBehaviorValidation` завершён с `PASS 38`, `TypedMainMenuValidation` — с `PASS 264`, `MainMenuPlayModeValidation` — с `PASS 31`. Последний — автоматизированный Editor PlayMode harness, не Test Runner или device QA. Локальный бой на примитивах реализован отдельно в BattlePrototype.unity: четыре роли, снаряды/зоны/смерти, fixed-step LeoECS, configs → definitions → passive pooled views. Три сценария проходят парные прогоны и критерий менее минуты; детали и runtime QA — Battle_Prototype.md. Полный локальный match/draft flow с подписанным ботом реализован: Local_Match.md. Network match prototype с pinned authority, per-recipient snapshots и PUN transport прошёл начальные Unity/Windows проверки полного матча, reconnect и recovery; evidence и ограничения — Network_Match_Prototype.md. Полная матрица синхронизации, онлайн-боты/матчмейкинг, backend, полный production UI и проверки на устройстве остаются открытыми. Превиз и runtime screenshots не являются финальным артом или подтверждением Android/iOS/manual touch UI runtime.

## Этап 1. Точная UI-разметка по референсу

24 reference frames приоритетного второго видеореференса приняты владельцем как стартовая композиция. Охват и таймкоды указаны в `Reference_Screen_Map.md`. Поддержка schema v2 groups/`parentId`, первая Unity-вёрстка главной и typed prefabs первой поверхности готовы; ещё 23 reference frames/состояния требуют отдельного переноса через MCP. Состояния из `UI_State_Map.md`, которых нет в выбранных кадрах, требуют отдельной вёрстки; адаптация к safe area проверяется на устройствах.

Локальный боевой прототип на примитивах с готовностью к замене арта реализован; локальный матч также готов; следующая сверка — темп драфта, читаемость армий и усилений, прежде чем подключать сетевой бой. Остальные UI/art блоки остаются в общем объёме; образцы финального арта не блокируют начало боевого runtime.

Проверка: исполнитель фиксирует в документации, какие экранные состояния реально сверстаны. Компиляция и геометрия подтверждают техническую целостность; runtime screenshot QA после MCP-переноса проверяет фактическую UGUI-вёрстку и не повторно утверждает уже принятую стартовую композицию.

## Этап 2. Ролевая таблица и направленный финальный арт

Составить таблицу «юнит референса → военная роль → formationRow → targeting/movement policy → ability». Для каждой записи указать источник наблюдения в референсе и статус: подтверждено, предположение либо требует решения. Ряды не смешивать ради внешнего сходства.

Сначала подготовить ViewCatalog и prefab-примитивы для боевой вертикали. Юниты, снаряды, попадания и зоны периодического урона должны быть видимыми с первого этапа; сменный арт не влияет на симуляцию. Затем подготовить 3–4 образца финального арта, покрывающие разные роли и редкость/состояние. Это образцы для выбора визуального направления, а не утверждение полного набора ассетов или баланса. При замене сохранить GUID prefab-контрактов и authoring flow.

Проверка: дизайнер/владелец сверяет таблицу и образцы с референсом; разработчик запускает content validator на уникальные ID, корректные ряды, ability references и ViewCatalog links. До такой сверки арт не помечается как approved.

Точка сверки: visual role/art mapping.

## Этап 3. Configs, validators и локальная вертикаль матча

Реализовано: `Local_Match.md`. Проверено 40 seeded матчей / 219 раундов: все завершены, `ReviewRequired` = 0, максимум 20.43 с; exact tie решается одним seeded authority roll с общим trace. Local Editor Play Mode: PASS 62 assertions. Это прототипный баланс, не восстановленная формула оригинала. Папки приведены к `Folder_Architecture.md`.

Создать Contracts, immutable definitions и authored каталоги для одной арены: четыре базовые роли, три варианта выбора в Offer, приказы, правила камбэка, раунд и матч до четырёх побед. Validators должны отклонять дубли ID, пустые prefab/ability links, недопустимый ряд, невалидные офферы и несовместимую версию контента.

Собрать LeoECS Lite vertical slice: `Queue → Offer → CommitChoice → Ready → SimulateRound → RoundResult → MatchResult`. Бой использует подготовленные pools/prefabs только для presentation; правила, урон, death, outcome и RNG остаются в simulation. Результат этапа — локально воспроизводимый матч с двумя сторонами, четырьмя рядами, тремя офферами, камбэком и итогом после четвёртой победы.

Проверка: automated tests для валидаторов и детерминированных сценариев; в Unity — runtime walkthrough со сбросом и повтором одного seed. Проверяющий показывает выбор каждого из трёх офферов, смену раундов и итог 4 wins. Успешная компиляция отдельно не считается доказательством gameplay.

Проверять балансными прогонами, что боевая фаза заканчивается примерно в пределах минуты без специального таймаута/овертайма. Незаходящие цели, застревание или бесконечное лечение — ошибки/проблемы баланса для диагностики, а не повод автоматически присуждать победу по HP. Проверить раздвижение юнитов и границы арены, видимый полёт снарядов, периодический урон зон и замену VisualRoot без изменения исхода.

Точка сверки: скрытые параметры генерации офферов. Для точной одновременной гибели последних армий принято правило одного seeded tie-break на authority с общим seed trace; не вводить ничью или client-local roll. Стадийность камбэка восстановлена по двум исходным видео: Draft_Comeback_Reference.md. Наблюдение владельца «мой последний лучник умер раньше — я проиграл, хотя его стрела затем убила противника» занесено в Reference_Gameplay.md; не вводить ничью из-за двух смертей в одном визуальном кадре. Вероятности и численные коэффициенты не выводятся из placeholder-превиза; один дополнительный выбор подтверждён последовательностями исходных видео. Полный предварительный расчёт боя не нужен: core принимает команды по ходу simulation ticks.

## Этап 4. Ранний двухклиентный PUN spike и authority

Выполнить параллельно с этапом 3, пока контент минимален. PUN 2 рассматривается как transport adapter, а не authority: отдельный validator/backend или match service принимает command envelope (`matchId`, `roundId`, `actorId`, `sequence`, `contentVersion`), проверяет фазу, deadline и легальность оффера, а settlement делает идемпотентно по `matchId`.

Результат этапа — два независимых клиента с одной комнатой и серверной/сервисной проверкой: normal выбор, поздняя команда, повтор sequence, reconnect в Offer и после RoundResult, retry settlement без второй награды. Для каждого случая сохраняется проверяемый trace команд и outcome. PUN AppId предоставлен и настроен локально вне Git; базовый транспорт уже проверен двумя Windows Player-процессами через Photon Cloud (комната, 20 request/ack и rejoin), см. Photon_Setup.md. Боевые команды, восстановление боевого состояния и settlement этим probe не проверяются. Релизная серверная топология ещё не выбрана.

Проверка: разработчик воспроизводит матрицу на двух клиентах; reviewer сверяет traces, неизменность награды после повторов и восстановление после reconnect. Риски authority, host migration и replay проверяются до наполнения контентом.
Network prototype проверен на двух Windows clients: baseline 410/410 common hashes и fault run 408 common revisions с intentional guest drop/resync/recovery, rejoin обеих сторон и 0:4. RTT/jitter/loss, max-load, device и release topology остаются открытыми.

Точка сверки: серверная топология PUN + validator/match service против альтернативы, с критериями защиты наград, reconnect, эксплуатации и стоимости.

## Этап 5. Полная мета и продуктовые экраны

Расширить вертикаль до коллекции, редкостей, уровней/мастерства, арен, командира, наград/паков, пропуска, рейтинга, профиля, косметики и настроек. Каждый экран получает ViewModel, команды presenter-а и состояния из `UI_State_Map.md`; pending блокирует повторную отправку, а error/retry сохраняет тот же operationId.

Результат этапа — end-to-end локальный поток: главная → коллекция/карточка/командир/магазин/пропуск/рейтинг/профиль и матч → результат → мета. Цены, баланс и entitlement не имитируются текстом UI.

Проверка: owner проходит сценарии экранов и состояний; automated tests покрывают use cases и migrations/save compatibility, когда формат сохранений будет введён. UI review и gameplay review проводятся отдельно.

## Этап 6. Live backend, платежи, реклама, баланс и боты

Подключить выбранный backend, persistence, серверную экономику, validation purchase/restore, rewarded ads, балансные конфиги и bot policy. Внешние SDK остаются Infrastructure adapters; credentials и live-конфигурации не попадают в репозиторий. Боты используют те же Contracts и format команд, что и два клиента, но не подменяют релизный PvP.

Результат этапа — staging-сценарий с валидируемым entitlement, единственным settlement, restore, rewarded flow, ботами при дефиците соперников и наблюдаемыми отказами сервиса. Реальные покупки, публикации и live-настройки выполняются только по отдельному поручению.

Проверка: sandbox/staging accounts, backend traces и отрицательные кейсы покупки/награды/повторов; владелец подтверждает economy/IAP перед включением live.

Точка сверки: economy/IAP до live.
